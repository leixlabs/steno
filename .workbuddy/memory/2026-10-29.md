## 接入 USB 麦克风后的实测（Razer Seiren，17:07 起）

**已跑通录音**，之前记的两个"阻断项"一个是误判、一个正确但可绕过：

- 硬件：`Razer Seiren`，card 1，`01-00 capture 1`；原生 48 kHz（`hw:1,0` 打不开 16k，
  必须走 plug）。`arecord --dump-hw-params` 注意：它会把音频写到 stdout，不要留 `</dev/null`
  否则刷屏（踩过）
- **真正根因（此前的推断是错的）**：服务账号 `snore-monitor` 不在 `audio` 组，
  打不开 `/dev/snd/controlC1`，ALSA 的 hint 列表**降级到只剩 `null` 一条**，
  所以 cpal 只看到 1 个设备、恰好选中 null。
  用 `sudo -u snore-monitor python3 alsa_hints.py`（ctypes 调 `snd_device_name_hint`）复现：
  pi 用户 15 个 input hint，服务账号只有 1 个。**修复：`sudo usermod -aG audio snore-monitor`**
- 加组后立刻暴露第二个问题（这个记录是对的）：17 个候选（1 null + 16 个同名 "Razer Seiren, USB Audio"）
  → `MultipleDevices`
- 无需改代码的绕过：`/etc/snore-monitor/config.toml` 写
  `alsa_device = "Razer Seiren, USB Audio"`（`==` 匹配 desc，16 个同名命中后 `.next()`
  取 hint 顺序第一个 = `default:CARD=Seiren`）。备份 `config.toml.bak.*`
- **修正一条旧记录**：cpal 0.18.2 **有** public `DeviceTrait::id() -> Result<DeviceId>`，
  DeviceId 实现 Display，能拿到 pcm_id（`default:CARD=Seiren` / `plughw:CARD=Seiren,DEV=0`）。
  之前"cpal 0.18 不暴露 pcm_id"是错的，按 pcm_id 匹配的改法完全可行
- 结果：`microphone=state:ok`、`recording=state:ok`，`/mnt/snore-monitor/recordings/2026/10/29/*.wav.partial` 持续增长
- **遗留缺陷（真问题）**：`xrun_count` 每 10 秒左右 +1（60 秒 6 次），`last_error=CPAL stream error:
  A buffer underrun or overrun occurred`，实测 60 秒只写进 61.98 秒音频（约缺 1.6%）。
  排查：`arecord` 用 `default:CARD=` / `sysdefault:CARD=` / `plughw:CARD=,DEV=0` 三种 PCM
  各直录 30 秒，**全部 0 overrun、字节精确 960044**；把 `period_ms` 10→20、`buffer_ms` 200→400 无效。
  → 硬件/驱动/ALSA 层干净，xrun 出在程序侧 cpal 流的消费线程
- 当前状态：服务 **stopped（仍 disabled，不开机自启）**；config 已含设备名 + 调整后的缓冲

## 采集端/服务端拆分落地（17:45）

把单机版拆成「采集端 + 服务端」，用同一 crate 的两个二进制实现，默认仍走 ALSA，现有部署行为不变。

- **新增**：`src/protocol.rs`（32B 头 UDP 线格式，手写编解码，含 10 个单测）、
  `src/net_capture.rs`（UDP 接收 + 重排 + 合成时间轴）、`src/bin/snore-node.rs`（采集端）、
  `tests/net_capture.rs`（4 个无需硬件的集成测试）
- **关键接口**：`CaptureRing::callback_push(&[i16], CaptureMeta)` 是采集层唯一生产者契约，
  网络来源复用同一函数 → dispatcher 以下（recorder/detector/storage/http）**一行未改**
- **时间轴决策（重要）**：`mono_start_ns = anchor_ns + (node_t_mono_us - t0_us)*1000`。
  用节点单调时钟而不是到达时间：① WiFi 抖动不会伪造 gap（`gap_tolerance_ms=20` 很敏感）
  ② 若用帧数反推，`clock_drift_ppm` 会恒等于 0，因为录音自身误差成了标尺
  为此把 `monotonic_now_ns()` 从 dispatcher 上移到 `timeline.rs` 作为唯一原点
- **失败模型**：丢包→序号缺口→重排窗口(150ms)到期跳过→dispatcher 记时长正确的 gap；
  会话变更（session_id 变 / 帧号大幅回退）→ 重建会话重锚时间轴；格式与 `[audio]` 不符 → 拒绝而非静默重解释；
  超过 `source.idle_timeout_ms` 无包 → `microphone=disconnected`
- **配置**：`[source] kind = "alsa"|"net"`；net 模式仍从 `[audio]` 取期望格式（单一事实来源）
- **验证**：`cargo test` 15 个测试目标全通过（111 库测试 + 4 新集成测试）；
  端到端用 Python 假节点发 12.000s → WAV 384,044B（= 44 + 192000×2），
  `packets_lost=0 protocol_errors=0`，节点停发 5s 后 `node_connected` 自动转 false
- **未验证**：真实 USB 麦 + WiFi 下 8 小时稳定性、Pi 上的 CPU/RSS、断网/重启恢复
- 文档：`docs/split-deployment-2026-10-29.md`、`node.example.toml`、`systemd/snore-node.service`
- 交叉编译注意：本机直接 `cargo build --target armv7...` 会因缺少 ALSA sysroot 失败
  （`pkg-config has not been configured to support cross-compilation`），需用 README 里的 `cross`

## 联调收尾：三个真实 bug（本机 server + 树莓派 node）
1. **节点离线后仍显示在线**（`net_capture.rs`）。收包分支里原本写的是
   `if !self.idle_reported { self.idle_reported = false; }`，条件反了，
   等于「第一次静默后永久锁死」：之后 `check_idle` 直接 return，
   `net_source_connected` 再也不会被清掉。改为收到包就无条件复位，
   并加测试 `a_node_that_comes_back_goes_offline_again_when_it_leaves`。
2. **正常分段被判成 `size_limit`**（`dispatcher.rs::maybe_rotate`）。字节上限
   `rate*channels*2*duration` 与帧上限同源，而 400ms 的块总是同时跨过两者，
   原来的顺序是先判字节 → 每个 10s 分段都记 `size_limit`。改为先判帧、字节做兜底。
3. **前端整页白屏**（`web/src`）。`Status.storage` 接口里写的是
   `recording_bytes`，后端实际返回 `used_bytes`，`bytes(undefined)` 在 render
   里抛 TypeError，React 19 直接把整棵树卸载。tsc 抓不到（类型是自说自话），
   只有真正渲染才暴露。修字段 + 把 `bytes()` 改成兜底返回 `—`。

## 转写改为常驻流式（21:00-21:20）
- **Dock 闪窗根因**：`stt` 每 10 秒为每个分段 `open -n -W -a snore-stt-apple.app`，
  没有 UI 的 bundle 被 LaunchServices 当一次前台应用启动 → 图标闪一下。
- **新架构**：一个常驻 helper（`--stream --socket PATH`），服务端 bind Unix socket
  再 `open -n -a` 拉起；双向协议：服务端→helper 是
  `[u32 len][i64 utc_ms][s16le PCM]` 帧，helper→服务端是逐行 JSON
  （ready/partial/final/error）。之所以用 socket 而不是 pipe：TCC 只认
  LaunchServices 拉起的责任进程，而 `open` 不把 stdio 交回来。
- **端点检测**：helper 内部按 RMS<400 计静音，连续 1.2s 静音就 endAudio 并重开
  task，否则只有 50s 轮转才出 final，一整晚就是一坨大段落。
- **存库**：schema v3 新增 `utterances`（绝对时间、文本、segments_json）；
  `POST` 无，查询 `GET /api/v1/utterances?date=`；`/status` 增加 `stt` 段
  （connected/engine/finals_total/dropped_blocks/partial/error）。
- **dispatcher** 增加第三条通道 `stt_queue`（可选、有界、溢出只计数），
  录音/检测永不被转写反压。
- **验证**：Swift 侧用 `tools/stt-stream-probe.py` 驱动，28.5s 中文音频出 1 条
  final、时间戳正确；服务端侧用假识别器 `/tmp/snore-stream/fake-stt.*` 跑通
  全链路（5 条语句入库 + API 返回）。`cargo test --workspace` 全绿。
- **卡点**：每次重编 .app，macOS 的「语音识别」授权就失效（cdhash 变了），
  而且从后台启动时 TCC 弹窗不出现（status 停在 notDetermined）。
  已加 `--authorize`（会起 NSApplication 并激活 120s）配合
  `tccutil reset SpeechRecognition dev.workbuddy.snore.stt`，
  但仍然没有弹出→ 需要人工确认一次。**未确认前线上 `[stt] enabled=false`**。
