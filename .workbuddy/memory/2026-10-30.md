## 项目更名为 steno（仓库与本地目录）

命名讨论的结论：原名 `snore-monitor` / 目录 `2610-snore-monitor-pi` 不准确，因为
`-pi` 描述的是硬件，而实际是 node/server 分离、服务端可跑在任意常开机器上。

更关键的是**系统真实行为与名字不符**：`storage.rs::segments_awaiting_transcript`

`segment_duration_seconds` 连续切分。即它是「全天候录音 + 全量转写 + 鼾声标注」，
而不只是鼾声监测器。

- 选定名 **Steno**（速记员）：同时表达「一直在场」和「不判断、只记录」，对应
  events are candidates, not a diagnosis 的伦理定位。排除 Nightjar（夜里动物，
  不覆盖白天）、Vigil（守灵歧义 + 监控 SaaS 重名）、Eavesdrop/Voyeur 类
  （把已被 `bind_address=0.0.0.0` 放大的攻击面写成品牌承诺）。

- 未改（待定）：crate 名 `snore-lib` / `snore-server` / `snore-node`、bin 名

## 新发现：SIGTERM 后进程不退出（真 bug，未修）

`http_server::serve()` 里 `axum::serve(...).await` 没有任何 graceful shutdown
句柄，`run()` 末尾 `server_thread.join()` 于是永远阻塞。表现：SIGTERM 后分段
正常以 `end_reason=shutdown` 闭合、`.partial` 也没留下，但进程一直挂着，
`/api/v1/status` 仍 200，只能 `kill -9` 或等 systemd 的 `TimeoutStopSec=30s`。
（`serve_without_capture` 用 `tokio::select!` 等停止信号，那条路径是好的。）
修法方向：`serve_until(state, shutdown_future)`，用 `axum::serve(..)
.with_graceful_shutdown(..)`，主流程在排空 DB writer 之后 `notify_one()`。

## 14:40 — 排查「识别器未连接」+ Portal 改造为控制中心

**根因（四层，前两层是误报）**：`/status.stt` 只有 `connected` 一个布尔，而它只在流式
worker 收到 helper 的 `ready` 后置位。于是「`[stt] enabled = false`（真没开）」、
「开启了但 helper 没连上」、「`mode = "segment"`（根本没有长连接）」三种情况渲染成
同一句话。另外 `config.example.toml` 的 `[stt]` 段缺 `mode`/`stream_command`/
`socket_path`，照示例只写 `command` 的人实际去启动的是 `snore-stt-stream`（默认值），
`command` 根本不被使用。helper 本身已装在 `~/.local`（`snore-stt-stream` +
`snore-stt-apple.app`），但 `~/.local/bin` 不一定在服务端进程的 PATH 里，且 TCC 授权
仍需人工点一次——`/tmp/snore-stt-apple.log` 最后一行是 `permission was not granted`。

**改动**
- `crates/lib/src/config.rs`：新增 `ControlConfig`（默认 `enabled=false`，
  `enabled=true` 只在 `server.bind_address` 为 loopback 时通过校验，否则点名报错）
  + 4 个单测。
- 新 `crates/server/src/control.rs`：只跑 `systemctl <verb> <unit>`；`Target`/`Action`
  是封闭枚举，单元名只来自配置；`/run/systemd/system` 不存在时返回
  `Availability::NoSystemd`，动作返回 403 带原因，不假装成功。带 5 个单测。
- `http_server`：`stt` 段加 `enabled`/`mode`/`state`（`stt_state()` 派生，顺序

- `storage.rs`：`pool_summary()` 一条 SQL 出 used/count/oldest/newest。
- **顺手修的真 bug**：`main` 优雅关闭最后 `server_thread.join()`，但没有任何东西让

  会被 `TimeoutStopSec` 兜底。加 `http_server::serve_with_shutdown` + `watch` 通道，
  实测 SIGTERM 后 ~2 秒 `shutdown complete` 退出。这也正是启停按钮能用的前提。
- 前端整页重写为控制中心：三张状态卡（服务端/采集端/转写）+ 存储池 + 录音浏览 +

  「net 源无节点时仍显示 有信号 / 录制正常」三处口径错误。
- `config.example.toml`、`tools/run-server.sh`（`--stt` / `--control`）、`AGENTS.md`、

## 14:50 — 重启 + 恢复扫描的路径 bug（重启才暴露）

重启前旧实例（旧二进制）`kill -TERM` 后 10 秒不退，只能 `kill -9` —— 正好印证上一节
修的那个 `server_thread.join()` 挂死。新二进制后被 TERM 约 1 秒退完（`shutdown complete`）。

**新发现的真 bug（`recovery::relative_to`）**：它把 `root.file_name()` 拼回相对路径前面，
即假定 DB 里的 `relative_path` 是相对 `recording_dir` 的**父目录**。但录制器
（`WavRecorder`）、播放（`get_audio`）、回收（`retention`）全都用
`recording_dir.join(relative_path)`，而 `segment_relative_path()` 生成的是
`recordings/YYYY/MM/DD/x.wav` —— 于是磁盘上是 `recordings/recordings/...`（多一层），
DB 里是 `recordings/...`。重启触发恢复扫描时两边永远对不上：39 个段被标 `missing`、
39 个文件被当 orphan，`pool_summary` 只统计 `complete/interrupted`，存储池显示 0 B。
恢复模块的 4 个单测当时是按错误布局摆文件的（`root/2025/...`），所以一直是绿的。

修法：`relative_to` 只做 `strip_prefix`；`reconcile` 新增分支——`missing` 行若文件又在了，
按 WAV 头部重新判定（`44 + declared == file_len` → `complete`，否则 `interrupted`），
这样被误判的库存能在下次启动自愈；单测文件布局改成真实布局，补两个回归测试
（录制器自己写的文件不算 orphan、missing 行可从文件恢复）。实测重启后 39 段恢复、
44 段 complete、池子 75.4 MB。

## 15:05 — 开启转写：Apple 流式识别 endAudio 丢整句

`[stt] enabled = true` 后 helper 连上、`state = ready`、partial 一直来，但 `finals_total`
恒为 0。用 `tools/stt-stream-probe.py` 直连 helper 复现：task 结束时回调
`kAFAssistantErrorDomain 1110 "No speech detected"` 且 `result = nil` —— `endAudio()`
把整句作废。同一段音频走文件模式 `snore-stt-apple <wav>` 完全正常（逐词时间戳都有）。

**踩过的三个坑（都留在 main.swift 注释里）**：
1. `endAudio()` 后立刻 `request = nil` → 请求可能在 final 到达前被释放。改成 retired
   队列。单独无效。
2. 补救时用同一个 `SFSpeechRecognizer`（甚至新实例）发 URL 请求 → 仍 1110。
3. 正解：**进程里只要还有活着的流式 task，文本请求就被拒**。补救前先停掉实时 task，
   期间的音频存 `pendingSamples`，补救完按 20ms 分块喂回新 task。

补救 = 用 task 自己的 PCM 写临时 WAV → 文件识别 → 照常发 `final`（真实起止 + 逐词
segments，不是拿 partial 拼）。没形成过 partial 的 task 直接跳过，夜里静音不浪费 CPU。

代价：每句多约 1 秒（只在收尾时跑，不影响录音主链路），partial 仍实时。

**验证**：旁路实例（UDP 8093 + 独立库）回放 `say` 合成的 8.8 秒中文，
`/api/v1/utterances` 得到 1 条 6.0 秒、15 个词级片段，页面「识别中 · 1 句」。线上实例
`state = ready`、房间安静故 0 句（正确）。Rust 侧只加了 stt_stream 的 debug 日志
（helper 发了 final / final 为何被丢），15 个测试二进制全绿。

顺带：helper 重装后 TCC 授权没有失效（ad-hoc 签名变更但 grant 仍有效）。

## 15:50 — 门控会把对话切碎：hangover 决定的是"语义单元"

用户质疑「只按电平发有声部分会把一段自然对话切碎」。用 104 分钟真实录音离线重放状态机验证，
成立，且数字很硬：

| hangover | 发送段/小时 | 段中位长度 | 剔除占比 |
|---|---|---|---|
| 2 s（当前默认） | 307 | 2.1 s | 47% |
| 10 s | 70 | 16.7 s | 13% |
| 20 s | 11 | 79.8 s | 3.5% |
| 30 s | 5 | 346 s | 1.5% |
| 60 s | 1.2 | — | 0.1% |

结论修正：`hangover_ms` 不是"尾音补偿"，它是**判定单元**——2 s 等于"一次爆发"，20–30 s 才
等于"一段对话"。当前默认落在错误的一端。缺的是两样东西：① 关闭计时器要长得多（close
而不是 tail）；② **合并规则**（上一段发送结束不足 X 秒就不要另起一个新片段）。

**更根本的冲突**：上行门控 ⇒ 服务端没有那段音频 ⇒ 服务端 STT 无法转写。所以"省带宽"和
"服务端转写"在架构上是对立的，除非把 STT 移到端侧、或事后补传档案、或只上传文字。
门控真正适用的场景是「3am 空房间」，不是「有人在说话」——对话占满时间，门控本来就省不到。

## 17:50 — tools/dev.sh：一个命令的开发环境

需求：前后端都能动态加载最新代码。前端本来就有 Vite HMR，后端没有——改一行 Rust 得
`cargo build` + 手动重启。

- 新脚本 `tools/dev.sh`：Vite :5173（代理 `/api`）+ 服务端 :8080；改 `web/src/**` 走 HMR，
  改 `crates/**/*.rs` 走 `cargo build` → SIGTERM → 起新的。
- **先构建后替换**：`cargo build` 是 rename 落盘，运行中的进程握着自己那份，所以只在构建成功
  后才发 SIGTERM。实测塞一行语法错误 → pid 不变、`/status` 仍 200；修好后自动重建。
- 运行目录复用 `var/`，页面看到真实分段；代价是占用 8080，退出提示用
  `refresh-all.sh --no-node` 放回常驻实例。
- `vite.config.ts`：代理目标改为 `VITE_API_TARGET`（`--port 8081` 时由脚本传入）；
  新增 `host: '127.0.0.1'`（Vite 默认解析到 `::1`，`127.0.0.1:5173` 会 connection refused）
  和 `strictPort`（5173 被占用时直接失败，不悄悄换端口然后代理到错误后端）。

**调试脚本时踩的三个坑（都是"测法错"而不是"脚本错"）**：
1. 用 `(cmd &)` 后台启动脚本 → POSIX 让后台任务继承 `SIGINT=SIG_IGN`（`ps` 的 `SNs+` 可看出），
   于是 `kill -INT` 完全无效。真实终端里 Ctrl-C 是发给前台进程组的，不受影响。
2. trap 里只做清理没 `exit` → 清理完回到重建循环继续等文件变更，进程"看起来关了其实还在"。
   加 `exit $status`。
3. `while ...; do sleep 1; done` 里 bash 在等**前台子进程**时不跑 trap，Ctrl-C 会被推迟。
   改成 `sleep 1 & wait $!`（`nap()`）。

**最终验证**（`script -q /dev/null` 分配真 pty，模拟真实终端）：
`printf '\003'` → `[dev] shutting down` → `[dev] stopping server pid 42728` → `shutdown
complete` → 脚本 exit 130 → 端口释放 → 无残留进程。TERM 同样路径。

`AGENTS.md` 新增 While developing。

## 19:00 — 前端改为 WebSocket 实时拿转写结果

Agentation 标注：「前端用 websocket 实时获取翻译结果」。原来靠 4 s 轮询 `/status.stt.partial`，
窗口太宽：partial 会被覆盖，短句甚至说完+final 了却一次没显示。

**服务端**（新增 `crates/server/src/transcript_hub.rs`）：
- `tokio::sync::broadcast` 通道，容量 256；`TranscriptEvent` 六种：`ready`/`partial`/`final`/`state`/`error`/`lagged`。
- STT worker 在三个点发布：识别器就绪、partial、**final 在 `save_utterance` 之后**（顺序反了客户端会显示被库拒绝的句子）。
- `GET /api/v1/transcript` 走 `WebSocketUpgrade`（axum 需显式开 `ws` feature，默认没有）；
  转写未运行时返回 **503 + 原因**，不开一个永远不说话的 socket。
- 慢客户端被丢最旧事件并收到 `lagged`，绝不反向阻塞录音链路。
- `/status.stt.stream_clients` 暴露订阅数，用于查连接泄漏。

**前端**（`src/liveTranscript.ts`）：
- 1s→2s→4s→10s 退避重连；`visibilitychange` 到 hidden 主动断开。
- `final` 按 `id` 去重（历史 HTTP 拉过的和推送的可能重复）。
- `useLiveTranscript(isToday && stt.enabled)`：非今天不连（socket 永远是"现在"），转写没开也不连。
- 面板新增一行流状态（实时/重连/落后 N 条/出错），否则"没有文字"分不清是安静、没连上还是漏了。

**修的问题**：
1. `vite.config.ts` 代理加 `ws: true`，否则 dev 态 upgrade 被当普通 HTTP，socket 永远打不开。
2. 头部句数用 `utterances.length` 而正文用合并后的数组 → 推送来的句子不进计数（实测 0 句 vs 正文 1 句）。
3. `duration()` 把 270 ms 的短句显示成「0 秒」，改成亚秒保留一位小数。

**验证**：
- 真 WS 客户端：`ready` → 5 个 `partial`（"现"…"现在是下午2:50这是一段用来验证语音转的"）→ `final`，SUMMARY `{ready:1,partial:5,final:1}`。
- CDP 驱动真实页面：BEFORE 0 句 → 回放语音 → AFTER 1 句，**未刷新**；头部 `1 句 · 6 秒` 与正文一致。
- 生产实例实测：页面开着时出现一句「需要」（270 ms），`连接时已有 0 句` 证明是推送来的。
- 503 守卫用**真实 TCP 握手**测试（`WebSocketUpgrade` 是提取器，无握手会先返回 426，测不到守卫）。

## 识别准确率：TTS 量化 + 采集端修复（20:00）

- 新建 `tools/stt-check.py`：TTS 语料（`say` + ffmpeg 降质模拟远场）→ file / stream 双通道路径 → 字符错误率。
  关键：苹果把"三点"输出成 `3:00`、"一百三十九"输出成 `139`，`normalize()` 做数字/时钟/语气词归一化，
  否则正确的输出会被算成 17% 错误。
- 结果：近场/远场 × file/stream 全是 **0.8% CER**，stream 与 file 逐句完全一致 → 流水线与引擎无罪。
- 真实录音的问题不在引擎：
  1. Razer Seiren 采集增益拉满（+22 dB），底噪 −33 dBFS 且能量几乎全在 250 Hz 以下 →
     节点加 120 Hz 二阶高通（`audio.rumble_highpass_hz`，默认 120），底噪降到 −41.7 dBFS。
  2. **`SFSpeechURLRecognitionRequest` 对长音频（60 s，含少量语音）直接返回空**，同一段走流式通路
     能出文本、切 10 秒后 file 接口也能出文本。而 `recover()` 与 `[stt] mode = "segment"` 都走它 →
     兜底一直在静默丢句子。改为 `FileRecognizer.recognizeSamples()` 分窗（10 s 窗 + 1 s 重叠 + 拼接去重）。
- 顺带修：`WireConverter`（设备 48k 立体声 → 16k 单声道，ALSA 会把 16k 请求悄悄改成 48k 而节点照旧标 16k）、
  `ArrivalGuard`（每秒到达帧数校验采样率，>5% 偏差报错并写进 node_report；开流前 3 s 不测，否则环形缓冲注水会误报）、
  UDP 非阻塞发送（阻塞会撑爆 500 ms 采集环，整句被撕开）、把 `1101 canceled` 从"错误"降级为"轮转"。
- 节点自报新增 `device_rate_hz`/`device_channels`/`ring_overflow_frames`/`send_errors`/`wire_frames`。
- 待人工：新 helper 换了代码签名，需 `open -n -a ~/.local/lib/snore-stt-apple.app --args --authorize` 点一次允许，
  之后重启 server 才会用上分窗识别。
