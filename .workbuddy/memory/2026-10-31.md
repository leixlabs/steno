## 顺手修掉的真 bug：单文件模式主线程死锁

`FileRecognizer.recognize` 用 `DispatchSemaphore.wait(25)` 等结果，而 SFSpeech 把回调投递到
主队列 —— 主线程被自己阻塞，回调永远排不进来，最后报"识别器没有结果"。
实测：同样 7 s 音频，裸信号量 25.5 s 空等，改成主线程 pump run loop 后 3.4 s 出 JSON。
影响 `[stt] mode = "segment"`：短于 11 s 的 16 kHz 文件从来没成功过。
（`recover()` 在音频队列上调用，不受影响，所以流式路径一直有字。）

## 根因确认：Pi 的采集流在 10-30 21:13 掉了，之后一直没恢复

- Pi 上 `snore-node` 进程**活着**（PID 11124，etime 16:54，14% CPU），仍按秒发 HELLO/INFO，
  所以服务端 `node_connected = true`、`packets_received` 以 ~2/s 增长 —— 看起来"在线"。
- 但 `/proc/asound/card1/pcm0c/sub0/status` 是 **closed**，节点自报的 `wire_frames`
  两次读数完全一样（886036668），即**没有任何 PCM 上线**。
- dmesg：`usb 1-1.3: new high-speed USB device number 23` —— Razer Seiren 重新枚举过。
  时间对得上最后一条日志 `2026-10-30T13:13:02Z ... not delivering the rate it reported`
  （observed 14761 Hz）。那条 ERROR 只是一次性记录，不影响采集；真正的问题是 **CPAL 流
  随 USB 掉线死掉后没有重建**，而节点对此完全静默。
- 后果链：无 PCM → ring 空 → dispatcher 不跑 DSP（`dsp.count = 0`）→ 无分段 → STT 队列空
  → helper 收到 **0 字节**（窗口里 0 块/s 就是证据）→ 无字幕。macOS 侧全程无辜。
- 临时处置：`sudo -n systemctl restart snore-node` → PCM 状态 RUNNING，服务端 packets 从
  169 跳到 919（~75/s），探测器离开 warming_up（noise floor -45.5 dBFS）。
- 待做的真修复：节点要能发现采集流已死并重开（或 `Restart=` + watchdog 兜住），
  现在是"进程活着但什么都不发"，silent failure，违反项目那条"不许静默降级"的精神。

## 观察到的流式路径事实（回答"实时翻译没结果"）

- 流式任务自己的 `endAudio()` 在这台机器上基本都返回 `kAFAssistantErrorDomain 1110`，
  且 `result == nil`；真正出字的是 `recover()` 里用文件路径重识别一遍。
  所以"某一句话从没出现过 partial"就永远不会有 final —— `recover` 要求 `lastPartial` 非空。
- 12:13 服务端已 `shutdown complete`（不确定是谁发的 SIGTERM）。停之前的状态是：
  `stt ready / connected` 但 `finals_total = 0`，`dsp.count = 0`、`detector warming_up`、
  最新完成分段停在 03:18 —— 也就是 UDP 包在收（`last_packet` 一直在跳），但帧没有进
  capture ring，问题在 net_capture → ring 这一段，不在识别器。

## 调查：界面文本 ≠ 流式识别文本（根因）

- 核对链：helper 日志 `/tmp/snore-stt-apple.log` = `server.log` 的 `utterance stored` = `var/db/app.db`
  = `/api/v1/utterances` = 助手窗口表格，**文本完全一致**。服务端（stt_stream/http/Portal）不改写文本。
- 真正根因：每个 50 s 任务 `endAudio()` 后 Apple 一律回 `kAFAssistantErrorDomain 1110`（无 result），
  日志里是 `recognition final: (empty) — retrying through the file path`；流式 partial 被丢弃，
  落库文本全部来自 `recover()` → `FileRecognizer.recognizeSamples`。
- 而 `recognizeSamples` 对 >11 s 音频走 **10 s 窗口 + 1 s 重叠、每窗独立解码**，再用
  `appendWithoutOverlap`（最多 12 字前后缀相同就截断）拼接，并返回 `segments: []`。
  证据：`windowed recognition: 6 windows, 50 characters`；DB 里 `SnapshotLet me doNo matter…` /
  `AbstractIs the verification` 是窗口拼接不补空格的铁证。
- 次生后果：`segments=[]` → `recover()` 用 `task.startUtcMs` 和 `samples/16000` 兜底 → 每条都是 50.0 s；
  utterance 起点=窗口起点（13:33:43.618），助手窗口显示=解码完成时刻（13:34:38.583），相差 ~50 s。
- 顺带发现：`var/server.log` 有 `recordings/recordings/…` 双前缀路径，segment WAV 写不进去
  （recorder i/o error），逐段转写路径因此拿不到文件。

### 转录按停顿合并成段（19:2x）

识别器每听到一个停顿就落一个 final，"我吗 / 我也 / 自播。/ 赛姆。/ 嗯。 / 嗯" 这种
两三个字的碎片一行一条，作为一列没法读。改成 `buildPassages()`：相邻句子间隔
≤ `PASSAGE_GAP_MS`（60 秒）合成一行，上限 2 分钟 / 32 句；左列时长为**各句时长之和**
（不是首尾跨度——跨度里是沉默），悬浮标题给精确起止和句数。行仍是跳转目标，跳到首句。

阈值取舍：实测一晚 296 句，gap 中位数 53 秒（所以 60 秒正好把"同一个停顿内的碎片"和
"过一会儿说的另一件事"分开），合并后 152 行；但对话里的效果远大于这个数字——15:08 那一段
三分钟里 19 个 final 变成一行。凌晨几分钟一次的"嗯"仍然各占一行，那是不同时刻的事，不该合并。
阈值是 `RecordingsPage.tsx` 顶部的常量，调一行就能变。

顺手：`buildPassages` 用 `Number.isFinite(ended)` 兜底，避免一个坏时间戳让 NaN 传染整组。

验证：用导出的真实数据离线跑合并（对比 15/30/45/60 秒阈值的行数与尾部排版）；生产构建上
CDP 点击合并行 → 选中 13:05 段、`currentTime` 33.3s、playing、行高亮。

### dev.sh stop（19:15）

`tools/dev.sh stop [role]`：本地执行（不进队列），不依赖监督器；按证据找进程：
监督器（活着则先停，走它自己的 cleanup 顺序）→ state 文件 + 8080 监听者（只认命令行带本仓库
`target/`）→ `steno-stt-<server pid>.sock` + socket 已消失的孤儿 sidecar → node/web →
还原 `[stt] stream_command` → 删 `var/dev/`。

修掉的四个 bug（都是这次实测暴露的）：
1. `echo $$ > supervisor.pid` 在客户端命令分支之前无条件执行 → `stop` 读到的是自己的 pid，

2. `pgrep -f ... | head -1` 在 `set -o pipefail` 下匹配为空时返回 1 → `set -e` 触发 EXIT trap

3. `wc -c < 缺失文件` 在 `set -e` 下中断启动 → 统一到 `log_bytes()`。
4. `state_pid` 在无 state 文件时返回非 0 → 统一 `|| true`。
5. dev 把 `[stt] stream_command` 指向 `var/dev/steno-stt-sidecar-dev`，stop 删掉该目录后

实测：无 supervisor / supervisor 活着 / supervisor 被 kill -9 / refresh-all 起的实例，四种都能清干净；

根因不是识别器，是**麦克风输出数字抖动**。Pi 上 `arecord` 直采峰值 −76 dBFS

3. 同脚本的 `alsa_device` / `[archive]` 只读新路径，未迁移设备（只有

## 重构：线上格式变成常量，16 kHz mono 只在采集端转换一次（20:3x）

用户要求「让 node 端直接上传 one 16 kHz mono buffer，也就是在采集端就输出 sidecar 需要的
数据流格式」，并选定：两条采集路径都归一化 + 保留选声道语义。

- `steno_lib::config` 新增 `WIRE_RATE_HZ`(16000) / `WIRE_CHANNELS`(1)，成为 wire、WAV、
  检测器、STT 队列、sidecar 共用的唯一格式。**不是配置项**。
- `[audio] preferred_rate_hz`/`channels` → `device_rate_hz`/`device_channels`，语义收窄为
  「向麦克风申请什么」。服务端 net 模式不再读它们来声明期望格式。
- `net_capture::NetCaptureConfig` 删掉 rate_hz/channels；HELLO 只校验是否等于 wire 常量，
  错误信息点名 wire 格式而非服务端设置。
- 单机路径新增 `audio_capture::LocalWireCapture`：CPAL 回调 → CaptureRing(device) →
  转换线程 → CaptureRing(wire) → dispatcher。回调里不重采样（音频线程不许分配/滤波）。
  设备环溢出通过 `CaptureRing::note_overflow_frames` 转记到 wire 环，gap 只记一次。
- `WireConverter::new(rate, channels, channel_index)`：downmix 从「所有声道求平均」改为
  「取 mono_channel_index 那一路」（这正是它一直号称在做的事）。下标越界返回
  `WireConversionError::ChannelIndex`，不 clamp。
- detector 的 `selected_channel` 固定传 0（wire 恒 mono）；`channel_mapping` 在 net 路径写
  `mono`（服务端不知道节点选了哪一路，写具体下标就是发明值），alsa 路径写 `mono:<i>`。
- `/status.microphone` 新增 `device_rate_hz`/`device_channels`，与 `capture_rate_hz`/
  `channels`（恒 16k mono）并列；web 控制台显示成 `48000 Hz · 2 ch → 16000 Hz · 1 ch`。
- 实测（net 真机回放 60 s）：3000 包零丢失、6 段 WAV 全部 16000/1；伪造 48 kHz HELLO →
  protocol_errors+1、错误信息写 "the wire format is 16000 Hz 1 ch"、零帧落盘。
- 单机路径在开发机跑不了：`select_device` 只收 S16，本机设备（Insta360 Link 2 Pro /
  MiRemoteV 2ch）只有 F32。由 `pipeline_e2e::a_48k_stereo_device_still_records_16k_mono`
  覆盖：48k 立体声、1 号声道带音、0 号静音 → 分发出去必须是 (16000,1)、3200 帧、峰值>1000。
- 部署影响：旧 `config.toml`/`node.toml` 会 `unknown field` 硬失败（有意，符合项目规则）。
  两个模板、`tools/deploy-node.sh`、`tools/run-server-mac.sh` 已同步。
- 全量 256 tests 通过；决策记录 `docs/decisions/2026-10-31-wire-format.md`。
