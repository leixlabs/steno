## web：候选片段 → 鼾声时间（聚合 + 回放）

- `web/src/RecordingsPage.tsx`：删掉按段列出的「候选片段」面板，改为整天的「鼾声时间」面板（`grid-area: snore`，跨两列）。
- 聚合：`buildEpisodes(events, gapMs, segments, source)`，唯一规则是「相邻记录间隔 ≤ 合并间隔」，默认 2 分，可切 30 秒 / 1 分 / 2 分 / 5 分。跨度、鼾声总时长、百分比、密度条（40 桶，按桶内被覆盖比例）全部由段内记录推出。单条记录不画密度条（只有一条时 40 根满格条没有信息量），画一条细线。
- 回放：一段 = 一串 cue（每条记录在它所在段里的偏移）。`seekToCue` 同段直接 seek，跨段换 `src` 靠 `pendingSeek` + `loadedmetadata` 落地；`onTimeUpdate` 判断越过 `endsAt` 前进，`onEnded` 兜住跑到文件末尾的 cue（用 segmentId 匹配防双跳）。实测 75 秒内 45 次 cue seek、6 次换段。
- 性能：`EpisodeTable` 用 memo + 稳定回调（`pickRef`），把 72 行 × 40 根柱从 `timeupdate`（4 Hz）的重渲染路径里摘出去。

## 关键发现：`snore_events` 有两路来源，混在一起就会把说话当鼾声

- `rule-v1`（10251 行）：服务端自己的检测器，频带能量高于噪声底就开一条。说话、电视、播放中的故事全都会触发——它回答「这里有声音」。
- `apple-soundanalysis-v1`（21 行）：sidecar 的 SoundAnalysis 鼾声通道（标签 `snoring` + 置信度阈值 0.5），日志确认通道是开的（`snore="snore(snoring@0.50)"`），但截至 11-02T01:43Z 之后没有再写入。
- 用户的原话「不是鼾声、只是录音也显示在鼾声时间里」就是这两路被混在一起聚合。现在面板按来源分开：默认分类器，当天没有分类器行时退到规则候选，并**在表头下方常驻一条琥珀说明**（rule-v1 只看能量，不是鼾声判定）；时间轴上另一路刻度淡到 0.28。
- `detector_version` 是 web 端唯一可用的判别字段（服务端 `EventView` 没暴露 `source` / `classifier_confidence`）。加字段要动 `http_server.rs`，这次没动。

- `sidecar_wire` 加 `write_frame_as(direction, …)`，`write_frame` 委托；原来写死 `ServerToSidecar`，侧车没法复用。
- 端到端：`tools/stt-stream-probe.py /tmp/qwen-long.wav` 三句与 11-02 记录逐字一致，跨度 6000/5920/6120 ms。`--check` 有模型 exit 0、无模型 exit 2。
- 两个真实坑：① 模型目录现在有 f16 + q8 两个 GGUF，引擎会拒绝，**必须传具体 .gguf 文件**；已在 `resolve_model` 里提前拒绝（之前是 spawn 之后才失败）。② 引擎的致命错误走 stderr（继承到服务端日志），stdout 拿不到，所以加了「reader EOF 且未 finish → 上报 session error」，否则死掉的识别器和安静的卧室分不清。
- **第三个坑（会死锁）**：`stt_stream::launch_sidecar` 原本用 `Command::status()` **等子进程退出**。Swift wrapper 是 `exec open -n -a`（立刻返回）所以没暴露；Rust 侧车是长驻进程，接进去会卡在 `accept()` 之前、整条 STT 链路一个字节都不流。已改成 spawn + 400 ms 宽限（早退非零 → Launch 错误；仍在跑 → 交给 reaper 线程 wait，防僵尸）。两个回归测试锁住两种形状。

- 已删除：`AudioCPPBackend.swift`、`wrappers/steno-stt-sidecar-audiocpp.sh`、Backend 的 `.audiocpp`/`Timing.window`、Options 的四个参数、Session/main 的 `audioCpp` 传参、install.sh 的 conf 逻辑。删后 `./build.sh` exit 0，`--backend audiocpp` 报 `unknown --backend audiocpp; expected apple`。

## `tools/dev.sh --backend audiocpp`（把两个环境变量收成一个 flag，已完成并验证）

- 起因：`STENO_STT_BACKEND=audiocpp STENO_STT_MODEL=<gguf> tools/dev.sh` 太长，人是记不住 60 多字的路径的。现在入口是 `tools/dev.sh --backend audiocpp`。
- 新增 flag：`--backend apple|audiocpp`、`--model PATH`（给了就隐含 audiocpp）、`--chunk N`。`STENO_STT_*` 三个环境变量原样保留作兜底（flag 优先），所以导出的环境或旧脚本不坏。
- 模型路径三级解析（`resolve_audiocpp_model`，只在 boot 里跑，`dev.sh stop` 这类 client 命令不会碰）：`--model` → 上次记的 `var/stt-model.conf` → `install.sh` 给已安装 wrapper 写的 `$PREFIX/lib/steno-stt-sidecar-audiocpp.conf`。命中一次就写回 `var/stt-model.conf`（`%q` 引号，读时 strip），所以第二次起真的只有一条命令；`dev.sh stop` 只删 `var/dev/`，这份 conf 留在 `var/` 根上。
- 目录歧义提前拒绝：`resolve_model_path` 复刻 `audiocpp::config::resolve_model`（本机那个目录正好有 f16 + q8 两个 GGUF，引擎会拒，所以必须在起进程前就拒并列出两个文件）。
- 矛盾组合直接 `die`：`--backend audiocpp` 配 `--stt off` / `--no-sidecar` / `--sidecar installed`（安装的 wrapper 是 Apple 那个）；`--model`/`--chunk` 配 apple；`--backend whisper`；`--chunk 60`。都是「安静地丢掉一个参数」会让人以为跑对了，所以宁可拒绝。
- **audiocpp 下不再构建 Swift bundle**：它在 `build_sidecar` 里走 `cargo build -p steno-server`（侧车是同一个 crate 的第二个 `[[bin]]`），`apple-stt-sidecar/**` 的 watcher 在该模式下也跳过——否则每次改 Rust 都会白建一遍 Swift。
- 验证（本机）：`tools/dev.sh --backend audiocpp --model <q8.gguf>` 起来 → `/api/v1/status` `stt.state=ready engine=audiocpp-qwen3-asr locale=zh-CN connected=true`，sidecar 日志 `audiocpp engine started chunk_seconds=5.0 language=zh`；`reload sidecar` 后仍是 ready；`stop` 后 `stream_command` 正常还原。第二次只给 `--backend audiocpp` 也起得来（命中了 `var/stt-model.conf`）。
- 同步文档：`tools/README.md`、`AGENTS.md` 开发循环段、`apple-stt-sidecar/README.md` 的「Selection is local」段、`docs/decisions/2026-11-03-audiocpp-sidecar-rust.md` 末尾加了补充说明。
