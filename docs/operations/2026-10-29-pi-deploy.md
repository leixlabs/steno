## 三、构建与安装

### 3.1 为什么不用 cross

`cross` 默认镜像基于 Ubuntu 20.04（glibc 2.31），产物在 buster（2.28）上会因
符号版本不足而拒绝运行；且 `ghcr.io` 拉取在本网络下卡住不动（8 分钟无进度，
无容器创建）。改用 `cargo-zigbuild`，可以直接把 glibc 钉在 2.28。

### 3.2 可复现的构建配方

`cpal → alsa-sys` 在 build script 里强制走 `pkg-config`，`rusqlite` 则回退到
`-lsqlite3`，所以需要一份 armhf 的链接期 sysroot（只需 `.so` 与 `.pc`，不需要
头文件）：

```sh
# 1) 从目标板取 armhf 运行库（Pi 上没有 libsqlite3-dev，直接拿 .so.0 更名即可）
SYS=~/armhf-sysroot
mkdir -p $SYS/usr/lib/arm-linux-gnueabihf/pkgconfig $SYS/usr/include/alsa
scp pi@<ip>:/usr/lib/arm-linux-gnueabihf/libasound.so.2.0.0  $SYS/usr/lib/arm-linux-gnueabihf/
scp pi@<ip>:/usr/lib/arm-linux-gnueabihf/libsqlite3.so.0.8.6 $SYS/usr/lib/arm-linux-gnueabihf/
cd $SYS/usr/lib/arm-linux-gnueabihf
ln -sf libasound.so.2.0.0  libasound.so
ln -sf libsqlite3.so.0.8.6 libsqlite3.so
cat > pkgconfig/alsa.pc <<EOF
prefix=/usr
libdir=$SYS/usr/lib/arm-linux-gnueabihf
includedir=$SYS/usr/include
Name: alsa
Description: ALSA (cross sysroot stub)
Version: 1.1.8
Libs: -L\${libdir} -lasound
Cflags: -I\${includedir}
EOF

# 2) 构建（glibc 版本后缀是关键）
rustup target add armv7-unknown-linux-gnueabihf
export PKG_CONFIG_PATH=$SYS/usr/lib/arm-linux-gnueabihf/pkgconfig
export PKG_CONFIG_ALLOW_CROSS=1
export RUSTFLAGS="-L native=$SYS/usr/lib/arm-linux-gnueabihf"
cargo zigbuild --release --target armv7-unknown-linux-gnueabihf.2.28
```

产物核对（部署前必做）：

```sh
file target/armv7-unknown-linux-gnueabihf/release/steno-monitor
# ELF 32-bit LSB pie executable, ARM, EABI5, dynamically linked,
# interpreter /lib/ld-linux-armhf.so.3, for GNU/Linux 2.0.0, stripped
objdump -T target/armv7-unknown-linux-gnueabihf/release/steno-monitor \
  | grep -o 'GLIBC_[0-9.]*' | sort -uV | tail -1   # → GLIBC_2.28
```

### 3.3 安装布局（本机实际值）

| 内容 | 路径 | 权限 |
|---|---|---|
| 二进制 | `/usr/local/bin/{steno-monitor,detect-wav,steno-eval}` | 755 root |

## 五、发现的问题

### 5.1 已修复（本次改动，均在仓库里）

**(a) `src/metrics.rs` — 32 位目标编译失败**

`buf.modes = STA_NANO` 中 `STA_NANO` 被声明为 `libc::c_int`，而 `struct timex.modes`
在 Linux 上是 `c_uint`。这段代码在 `#[cfg(target_os = "linux")]` 里，开发机是
macOS，所以从未被类型检查过；armv7 首次编译即报 E0308。已改为 `c_uint` 并加注
释。**这也说明该分支此前从未在 Linux 上编译过**，`probe_time_synced()` 的实际
行为属于首次验证。

**(b) `deployment/systemd/steno-monitor.service` — `ExecStartPre` 路径写死**

`/usr/bin/mountpoint` 在 Debian/Raspbian 上位于 `/bin/mountpoint`，导致单元在
`status=203/EXEC` 上失败，服务根本没被执行（`restart` 5 次后放弃）。已改为
`/bin/sh -c 'mountpoint --quiet /mnt/steno-monitor'`，跨发行版都成立。

**(c) `deployment/systemd/steno-monitor.service` — 崩溃循环保护失效**

`StartLimitIntervalSec` / `StartLimitBurst` 写在 `[Service]` 里，systemd 241
（buster）只认 `[Unit]`，日志明确 `Unknown lvalue ... in section 'Service', ignoring`。
即"5 分钟内失败 5 次就停"这条保证在目标板上完全没生效。已移到 `[Unit]`
（`systemctl show` 现在读到 `StartLimitIntervalUSec=5min`、`StartLimitBurst=5`）。

### 5.2 阻断真实录音：`audio.alsa_device` 匹配的是设备描述而不是 PCM 名

`select_device()` 用 `d.to_string()` 与 `config.alsa_device` 比较，而 cpal 0.18 的
ALSA `Device` 的 `Display` 实现返回的是 `description().name()`（人类可读描述），
真正的 PCM id（`hw:CARD=1,DEV=1`、`null`、`default`）在私有字段 `pcm_id` 里，
没有公开访问器。实测：

```
alsa_device = "hw:CARD=Loopback,DEV=1"  → requested input device ... was not found
alsa_device = "plughw:CARD=Loopback,DEV=1" → not found
alsa_device = "hw:1,1"                  → not found
alsa_device = "default:CARD=Loopback"   → not found
```

而 README 的排障章节正是让人填 `hw:1,0`。连带后果：

- 留空时，`input_devices()` 在真实板子上会返回"`null` 伪设备 + 麦克风"≥2 个，
  触发 `MultipleDevices` 拒绝启动；
- 填 `hw:x,y` 永远匹配不到，触发 `DeviceNotFound`。

**也就是说，插上真实 USB 麦克风也不会录到东西，这是 T8.1 的第一块拦路石。**
建议的修法（未实施，需要改接口语义）：给 cpal 提 `pcm_id()` 访问器，或在该项目
里绕过 `Display`——例如让 `alsa_device` 按"包含匹配"同时接受描述字段，并允许
用 `hw:` 前缀直接构造设备；再不然退回 `alsa` crate 自己做枚举。这属于设计决策，
没有现场改。

### 5.3 每次启动都会留下一个"0 帧但 complete"的空分段

无可用采集设备时，dispatcher 已经起来并开启了一个 segment；采集流失败进入
`serve_without_capture`，关闭流程把这个 segment 正常 finalize —— 于是
`recording_segments` 多一行 `status='complete', frame_count=0, size_bytes=44`，
磁盘上多一个 44 字节的 WAV。可复现：删库删文件后启动一次，必然出现一行。

```
('complete', 0, 44)
```

多次重启后累积，Portal 的日期列表里会出现一堆 0 秒、点了播不出的片段。建议：
`frame_count == 0` 的 segment 在关闭时删文件删行，或落成 `interrupted` 并标注
不可播放。

同时观察到配对的反向问题：把这些文件的行标成 `missing` 后，启动扫描每次都会
把"文件其实还在"的这些文件报成 `WAV file has no database row`（孤儿），
`missing` 状态从不被翻回。tasks.md T3.6 里这条本来就是未完成项，此处只是确认
了现象。

### 5.4 观察项

- **`service.state` 在同样条件下会在 `ok` / `degraded` 之间摆动**：连续两次
  `restart`，`microphone=disconnected` + `last_error` 非空，一次报 `ok`、一次报
  `degraded`。状态推导不纯粹是当前状态的函数。
- **`steno-eval` 默认参数在 5 s 片段上 recall=0**：`noise_floor_min_seconds`
  默认 10 s，而语料每段 5 s，预热从未完成，噪声底恒为 `null` → 无事件。这是
  语料与默认参数的错配，不是检测器缺陷，但用这套语料评估时必须显式下调预热。
- **ESC-50 语料只有正样本**（40 段全是 snoring，0 个对照），所以 precision
  1.000 是无意义的——假阳性率完全未测。任何"准确率"结论都不能出自这份语料。
- **`recordings/recordings/` 双层目录**：`segment_relative_path()` 生成的是
  `recordings/YYYY/MM/DD/...`，再拼到 `recording_dir` 后面，于是实际路径是
  `/mnt/steno-monitor/recordings/recordings/2026/10/29/...`。与 README 的写法一致，
  但看起来像 bug，容易在排障时被误判，值得在文档里点明。

## 六、未验证项与下一步

必须等真实 USB 麦克风（T8.1 起）：

1. 插上麦克风，`arecord -l` 记下 card/device → 填 `audio.alsa_device`。**注意
   5.2：当前填了也不会生效**，要先修设备选择。
2. 麦克风实际支持的 format/rate/channels，协商与回退路径是否按 48 kHz → 44.1 kHz
   降级。
3. CPAL 是否给出可靠捕获时间戳（`estimate_source`、`gap_detection_limited`）。
4. 8 小时连续运行：RSS < 80 MiB、DSP < 单核 10%，并据实测敲定 `opt-level`。
5. 无 RTC 的时钟行为：断网开机 `unsynced` → NTP 同步后的阶跃轮转。
6. 阈值校准（`detect-wav` + 真实整夜录音），并至少准备带负样本的语料。

现在这台机器上服务是**装好并开着的**（`enabled` + `active`），只是处于
"没有麦克风"的降级态；Portal 在 `http://192.168.31.58:8080/`。
